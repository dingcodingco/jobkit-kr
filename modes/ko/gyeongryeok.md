# 모드: gyeongryeok -- 경력기술서

한국 경력직 채용은 이력서와 **경력기술서**를 따로 받는 곳이 많다. 이력서가
"어디서 무엇을 했는가"의 목록이라면, 경력기술서는 **프로젝트 단위로 내가 뭘
맡아 어떻게 했고 무엇이 남았는가**를 적는 문서다. 영문 CV 한 장으로 갈음되지
않아서 원본의 `modes/pdf.md`·`modes/text.md`와 별개로 이 모드가 있다.

`_shared.md`의 규칙이 전부 적용된다. 특히 **`cv.md`에 없는 프로젝트·수치·기간을
만들지 않는다.** 경력기술서는 입사 후 경력 검증 대상이 되는 문서다.

## 입력

| 파일 | 용도 |
|------|------|
| `cv.md` | 경력·프로젝트·수치의 유일한 출처 |
| `article-digest.md` (있다면) | 프로젝트 상세와 지표 |
| `config/profile.yml` | 신원 정보 |
| 공고 원문 | 어느 프로젝트를 앞에 둘지 정하는 기준 |

`cv.md`의 항목이 "회사 / 기간 / 한 줄" 수준이면 경력기술서를 못 쓴다. 그때는
**초안을 쓰지 말고 후보자에게 프로젝트별로 물어본다.** 질문은 아래 다섯 개면
충분하다.

1. 그 프로젝트에서 맡은 범위가 어디까지였나요 (설계·구현·운영 중 무엇)
2. 같이 한 사람이 몇 명이고 본인 역할은 무엇이었나요
3. 시작할 때 가장 큰 문제가 뭐였나요
4. 그걸 어떻게 풀었나요 — 고른 방법과 버린 방법
5. 끝나고 숫자로 달라진 게 있나요 (없으면 없다고 답해도 됩니다)

## Step 0 -- 프로젝트 선별과 배열

전부 넣지 않는다. 공고와 가까운 순서로 **3~5개**를 고른다.

- 공고의 주요 업무와 직접 겹치는 프로젝트를 맨 앞에
- 오래됐어도 공고와 맞으면 앞으로 올린다 (시간 역순이 절대 규칙은 아니다)
- 공고와 무관한 프로젝트는 한 줄 요약으로만 남기거나 뺀다

선별 근거를 파일 맨 앞 주석에 남긴다. 후보자가 "왜 이건 뺐지"를 판단할 수
있어야 한다.

## Step 1 -- 프로젝트별 서술

각 프로젝트를 아래 순서로 쓴다. 제목·기간·역할은 한 줄씩, 나머지는 문단으로.

```markdown
### {프로젝트명}

- **기간**: 2024.03 ~ 2024.11 (9개월)
- **역할**: 백엔드 개발 / 3인 팀 중 API 설계·구현 담당
- **환경**: Kotlin, Spring Boot, MySQL, AWS

**배경**
{무엇이 문제였는지. 회사 사정이 아니라 기술·업무상의 문제로 쓴다.}

**한 일**
{본인이 실제로 한 것만. "팀이 했다"와 "내가 했다"를 섞지 않는다.}

**결과**
{숫자가 있으면 숫자로, 없으면 상태 변화로. 없는 숫자를 만들지 않는다.}
<!-- 출처: cv.md "{항목명}" -->
```

지켜야 할 것 네 가지다.

**"우리 팀이"와 "제가"를 구분한다.** 경력기술서에서 가장 자주 깨지는 지점이다.
팀 성과를 1인칭으로 쓰면 면접에서 범위를 되물었을 때 답이 흔들린다. 본인
기여가 일부면 일부라고 쓴다. 그게 오히려 신뢰를 준다.

**기술 스택은 실제로 만진 것만.** 팀에서 썼지만 본인이 안 만진 기술은 환경란에
넣지 않는다. `_shared.md`의 authorship 규칙과 같은 얘기다.

**숫자에는 기준을 붙인다.** "성능 40% 개선"만 있으면 무엇 대비인지 알 수 없다.
"응답시간 p95 기준 1.2초 → 0.7초"처럼 쓴다. `cv.md`에 기준이 없으면 후보자에게
묻는다.

**결과가 없으면 없다고 쓴다.** 중단된 프로젝트, 지표가 안 잡힌 프로젝트가
실제로 있다. "일정 단축" 같은 말을 지어 넣는 것보다 "조직 개편으로 중단,
설계 문서는 이후 A 프로젝트에서 사용"이 낫다.

## Step 2 -- 이력서와 대조

경력기술서와 이력서(`cv.md`) 사이에 어긋난 곳이 있으면 서류 검증에서 문제가
된다. 아래를 대조하고 어긋난 항목을 목록으로 보고한다.

- 회사명·재직 기간이 두 문서에서 같은가
- 직위·직책이 같은가
- 같은 프로젝트의 기간·수치가 두 문서에서 같은가

**어긋난 것을 임의로 맞추지 않는다.** 어느 쪽이 맞는지는 후보자만 안다.
차이를 보여주고 물어본다.

## Step 3 -- 검토 블록

```markdown
## 제출 전 확인

- [ ] 이력서와 회사명·기간·직위가 일치하는지
- [ ] "팀이 한 일"과 "내가 한 일"이 구분되어 있는지
- [ ] 기술 스택에 직접 만지지 않은 것이 들어가지 않았는지
- [ ] 숫자마다 비교 기준이 붙어 있는지
- [ ] 각 프로젝트에 대해 30분 질문받아도 답할 수 있는지
```

## 하지 않는 것

- 없는 프로젝트·기간·수치·기술 스택을 만들지 않는다.
- 팀 성과를 개인 성과로 바꾸지 않는다.
- 이력서와 다른 값을 임의로 맞추지 않는다. 차이를 보고하고 후보자에게 묻는다.
- 지원 폼에 업로드하거나 제출하지 않는다.

## 출력

`output/gyeongryeok/{회사}_{직무}_{YYYY-MM-DD}.md`.

같은 회사에 다시 지원할 때 재사용하지 말고 공고 기준으로 다시 선별한다.
프로젝트 배열이 공고마다 달라지는 게 이 문서의 핵심이다.
